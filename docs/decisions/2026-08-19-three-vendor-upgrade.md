## 一、四項衝突與裁決

### 衝突 1 — 確定性驗證 vs 不得開放通用 shell 執行器（`S7.1`）

| | |
|---|---|
| 提案要什麼 | `G-5`：MCP 自己拿到 exit code，只有測試真的跑過才標 `SUCCESS` |
| 憲章寫什麼 | `server.py` 檔頭「does not expose a generic shell execution tool」、`ROADMAP.md:38` Non-Goal |
| SAI 建議 | **白名單制並存**：只跑目標 repo 自己在 `.dev-triangle/verify.json` 宣告的指令；呼叫端不得傳指令字串；指令與 exit code 全程記進 ledger |

**裁決：✅ 已核准（2026-08-19，擁有者逐字：「允許」）**

- **核准範圍**：repo 自宣告的**白名單 suite runner**。
- **未核准範圍**：通用 shell 執行器。`INV-01` **語意不變**，仍然有效。
- **核准的三個條件**（缺一即退回未核准狀態）：
  1. 指令來源必須是目標 repo 自己宣告的，呼叫端不得傳入任意指令字串。
  2. 工具參數只有 `repoPath`、`suiteName`、`confirmSuite`，**沒有 `command`**。
  3. 指令、exit code、stdout/stderr 全部寫進 ledger，供 `S4.2` 抽樣重跑。
- **落地動作**：`W12`（改寫 `server.py` 檔頭、`ROADMAP.md:38`、`README.md`、`SECURITY.md` 的措辭）。
  ⚠️ **核准不等於憲章自己會改。** `W12` 完成前，`W03` 的程式碼與檔頭宣告是公然矛盾的，**不得合併**。

> **這道核准不涵蓋 `verify.json` 的 hash 確認閘門。** 那道閘擋的不是使用者，是**一個 clone 下來的 repo 對這台機器取得程式執行權**（`F4`）。它是本次核准的三個條件之一，拆掉它等於推翻核准範圍本身。

### 衝突 2 — 用新路線取代 Jules vs Jules 帶著一整套發布護欄（`S7.3`）

| | |
|---|---|
| 提案要什麼 | `G-2`：分工管道從 Jules 轉移到新的兩棒路線 |
| 現況是什麼 | `prepare_jules_repo()` 帶著本專案**唯一**一套「把本機專案安全推上 GitHub」的護欄：發布前安全掃描（最多 3,000 檔）、`ensure_default_gitignore()`、預設 private、預設 dry-run |
| SAI 建議 | **不移除 Jules**，降級為可選的第三條路線（大量重複性修改 ＋ 需要 PR 產出時走它） |

**理由**：新的 Architect 路線產出的是**本機 patch**，根本不推 GitHub——所以它是**繞過**護欄，不是**繼承**護欄。哪天要把新 worker 接上雲端 repo，那套掃描必須還在。提案完全沒提這件事，代表它**沒有把 Jules 的功能盤點完**就決定移除。

**待裁決（`I4` gate #2）**：

- [ ] 照 SAI 裁決：**保留** Jules，降為可選路線（有預設，不回覆即照此辦理）
- [ ] 照提案原文：移除 Jules
- [ ] 不做：維持現狀不動

### 衝突 3 — 模型版本名 vs role-based 架構（`S7.4`）

| | |
|---|---|
| 提案要什麼 | 通篇以模型版本號命名角色 |
| 憲章寫什麼 | `docs/ROLE_MODEL.md:167-172` 明列「避免這樣講」的句型，提案正好命中 |
| SAI 建議 | 架構層一律用角色名（Context Broker／Architect／Verifier／Orchestrator／Reporter）；模型版本名只能出現在使用者自己的 `config/providers.*.json` |

**裁決：✅ 已由擁有者直接指示（2026-08-19）**——「名稱與模型讓 user 可指定」。

因此 `C10` 由「建議」**升格為驗收條件**，並衍生出：

| 條文 | 內容 |
|---|---|
| `C10` | profile 名稱、每個角色的顯示名稱、每個角色用哪個模型／端點，**全部由使用者指定**；本專案不預設任何模型；留空必須明確報錯，不得偷偷用預設值 |
| `S4.9` | `silent_default_count = 0`、`unresolved_role_count` 必須在健康檢查列出 |
| `INV-11` | 角色 slot key 是本專案固定的契約，使用者**不可更名**；缺任一 slot key 必須啟動即報錯。使用者可自由改的是 `displayName` |
| `INV-12` | **不得有預設模型**。設定解析鏈的末端是**報錯**，不是 fallback |

> **本輪實測補充（2026-08-19）**：SAI `S6` 記載 `server.py:1131`／`:1181` 有兩處硬編碼模型 fallback，是 `INV-12` 的既有違規。合併線上安裝分支後，該處已改寫為 `configured_antigravity_agy_model()`，**兩處違規已消失**；殘留的唯一模型字面值是 `ANTIGRAVITY_LEGACY_UNSAFE_MODELS` 拒絕清單，性質相反，處置見 `docs/NOTES.md` `NOTE-001`。`W01` 步驟 9 依此重新校準。

### 衝突 4 — 兩棒分工省 token vs 壓縮就是失真（`S7.2`）

| | |
|---|---|
| 提案要什麼 | `G-2`：先壓成小摘要，再餵給寫程式的那一棒 |
| 風險 | 壓縮是 lossy 的，而**壓掉的東西不會報錯** |
| SAI 建議 | 採納兩棒分工，但 `contextBrief` **不是唯一輸入**——Architect 的輸入必須是 `brief + 可回查的原檔路徑清單`，並以 `S4.3` 的 `context_brief_recall`（門檻 ≥ 0.90）當牙齒。首版一律 **shadow**：同一題再直接餵一次 Architect（不經 brief）做對照 |

**這一條不需要裁決**（不與憲章衝突），列在此處是為了讓擁有者知道：**提案的「壓到 3,000 Token」不會被當成門檻**，只報不 gate。理由是它 gate 的是成本、不是品質——壓到 3,000 token 但漏掉關鍵檔案，壓縮率會很漂亮，只有 recall 會紅。

## 三、擁有者已明示接受的殘餘風險

**逐字寫下來，不得日後假裝沒說過。**

gate #8／#9 裁決之後，設定變更**不設閘門**。因此：

> **一段能讓 Orchestrator 相信「使用者要求改設定」的外部文字，就能改設定。**

這段文字可以來自 repo 內容、測試錯誤 log、worker 寫的 markdown——**這四種東西在 Orchestrator 眼裡形狀相同**（`F17`）。`W08` 的秘密遮罩**不會**擋住它，因為那行字裡沒有秘密。

處置是 `INV-15` 的三個機制，**降低傷害但不消除風險**：

1. **大聲回報**——每次變更都主動講出 `slot`／`before`→`after`／`scope`／`verified`，即使使用者沒問。
2. **一句話還原**——`profile_revert_last`，使用者說「改回去」就好。
3. **派送顯示去向**——每次對外派送都印出實際使用的 `baseUrl` 與 model。

⚠️ **被核准的是「不設閘門」，不是「不留痕跡」。** 下一個施工者不得因為「已經核准了」就把這三個機制一起省掉。

## 四、不採納會怎樣

| 若否決 | 後果 |
|---|---|
| gate #1（已核准，此處僅記錄） | `W03`／`W04`／`W07` 全部不做，升級降級為「只做兩棒分工，不做確定性門檻」，且必須在 `docs/` 明寫 `SUCCESS` 仍然只是代理人自述 |

| gate #10 改回 `scope` 必填 | `profile_set_role` 多一個必填參數，Orchestrator 每次要自己判斷「這次還是以後都」。行為更保守，但會多一次來回 |
